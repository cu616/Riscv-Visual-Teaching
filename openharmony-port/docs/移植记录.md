# OpenHarmony / 香橙派移植记录

日期：2026-05-05

## 1. 目标

将当前非 Blockly 自研积木教学应用移植到香橙派 OpenHarmony 环境。采用 ArkWeb 承载静态 Web 的方式，避免重写拖拽和吸附系统。

新增维护脚本：

| 命令 | 作用 |
| --- | --- |
| `npm.cmd run oh:sync` | 从根目录 `app/` 同步静态资源到 OpenHarmony rawfile，并自动恢复移植版 CSS、桥接脚本和数据流 stub。 |
| `npm.cmd run oh:smoke` | 检查 OpenHarmony rawfile 页面和关键资源是否齐备。 |
| `npm.cmd run oh:check` | 先同步再烟测，是每次真机构建前推荐执行的命令。 |

## 5. 风险

- 香橙派型号和 OpenHarmony 镜像不同，ArkWeb 可用性可能不同。
- rawfile 相对路径在 ArkWeb 中需要真机确认。
- 触控拖拽和鼠标拖拽手感可能不同，需要板卡上调阈值。
- 当前移植版仍主要依赖 Web 文件导入/导出，原生文件体验尚未完成。

## 6. 后续建议

1. 先用 DevEco Studio 在模拟器或本机 OpenHarmony 设备上构建。
2. 再用 HDC 部署到香橙派。

4. 原生保存/导入完成后，再考虑把部分状态面板 ArkUI 原生化。

## 8. 当前关键经验摘要

- OpenHarmony 工程级 `build-profile.json5` 中，`runtimeOS: "OpenHarmony"` 时，`compileSdkVersion`、`compatibleSdkVersion`、`targetSdkVersion` 必须是数值。当前本机 SDK 是 API 24，因此三者均配置为 `24`。
- `compileSdkVersion` 需要放在 `app.products[0]` 下；DevEco 报“请在 product 字段下配置 compileSdkVersion”时，优先检查层级。
- `AppScope/app.json5` 引用的是 `AppScope/resources/base/` 下的应用级资源，不是 `entry/src/main/resources/base/` 下的模块级资源。
- `ohos_electron_hap/` 是工程结构参考，不是当前主线替代方案。当前仍坚持 ArkWeb rawfile 轻量路线。
- RV2 HDC 接线使用 USB2.0 公对公数据线连接 RV2 的 USB2.0 HOST/DEVICE 口；Type-C 仅作为供电口。

## 9. 2026-05-06 命令行构建推进记录

本轮继续推进 DevEco / hvigor 侧验证：

- 新增本机 `local.properties`，解决 hvigor 找不到 `sdk.dir` 或 `OHOS_BASE_SDK_HOME` 的问题。
- 发现 DevEco SDK 实际安装为 `openharmony/ets`、`openharmony/js` 等扁平目录，而 hvigor API 24 期望 `openharmony/24/ets` 等目录。
- 在项目内新增本地 SDK 镜像 `.oh-sdk/24/*`，用 junction 指向真实 DevEco SDK 组件，并让 `local.properties` 指向 `.oh-sdk`。
- `openharmony-port/hvigor/hvigor-config.json5` 增加 `"hvigor.dependency.useNpm": true`，避开 pnpm 自动安装链路。
- 移除 `entry/build-profile.json5` 中错误的 `arkOptions.apPath`。该字段必须指向 `.ap` 文件；当前项目没有自定义 `.ap`，应交给默认流程。
- `hvigor --sync` 已能通过。
- `assembleApp` 已推进到 `:entry:default@CompileResource`，说明前面的 profile、resource 处理和 loader json 生成已经通过。
- 当前 Codex 沙箱中最终失败为 `Tools execution failed. spawn EPERM`，属于外部资源编译工具被沙箱拦截。下一步应在 DevEco Studio 或有完整本机权限的 PowerShell 中继续构建。
- DevEco 真机运行曾报 `00401004`，提示设备 `rpcid.json` 不包含若干 API 24 系统能力，例如 `AVTranscoder`、`FusionConnectivity`、`BackgroundProcessManager`、`ArkUI.Circle`、`PerfTest` 等。项目已新增 `entry/src/main/syscap.json`，通过 `production.removedSysCaps` 移除这些当前应用不需要的能力。重新生成后，报错列出的能力已从 `entry/build/default/intermediates/syscap/default/rpcid.json` 中移除。
- RV2 真机通过 HDC 读取到的系统版本为 OpenHarmony 5.0.0.71，`const.ohos.apiversion = 12`，`const.ohos.releasetype = Release`。因此项目已将 `compatibleSdkVersion` 和 `targetSdkVersion` 调整为 `12`，并设置 `compatibleSdkVersionStage: "release"`。
- 当前 DevEco SDK 只有 API 24 Beta1 元数据。为了让 HAP 的 `pack.info` 与 RV2 的 Release 镜像匹配，`oh:setup-sdk` 会在 `.oh-sdk` 本地镜像中把组件 `oh-uni-package.json` 的 `releaseType` 映射为 `Release`，不修改 DevEco 安装目录。重新生成后 `pack.info` 已变为 `compatible: 12`、`target: 12`、`releaseType: Release`。

构建前仍需先跑：

```powershell
npm.cmd run oh:check
```

## 10. 2026-05-06 真机运行与交互适配记录

本轮已在香橙派 RV2 OpenHarmony 5.0.0.71 设备上打通签名安装与启动：

```text
entry-default-signed.hap
bm install 成功
aa start 成功
com.riscv.visualteaching successfully launched
```

已解决或绕过的问题：

- DevEco 自动签名最初生成 `entry-default-unsigned.hap`，设备安装时报 `no signature file`。后续通过签名配置和本地 SDK 镜像中的 Profile 模板包名修正，已生成 `entry-default-signed.hap`。
- 首次完整页面启动时曾出现 `cppcrash-com.riscv.visualteaching`，崩溃点在 ArkWeb 系统库 `ArkWebHandlerImpl::OnNativeEmbedVisibilityChange`。通过 `app-smoke` 和 `arkweb-diagnostics` 分层页面确认 ArkWeb 基础能力可用，完整页面也可稳定加载，后续保留诊断页用于复测。
- 设备同时出现过 `cppcrash-usb_host`，崩溃模块为系统 `usb_host`，与应用进程崩溃分开记录，不直接归因到业务代码。
- 1024x600 7 寸 HDMI 屏下，原桌面三栏布局过宽且会触发移动端堆叠。当前 OpenHarmony 专用 CSS 恢复为左到右三列：左侧积木栏、中间拼接区、右侧机器状态/备注，下方为预览和日志。
- 顶部调试按钮已恢复为紧凑横向工具栏，避免“单步执行/自动执行/暂停”等按钮一项占一行。

交互适配现状：

- 点击式编辑已可用：点击指令积木可加入编辑区；点击寄存器/立即数/标签可选中；再点击匹配槽位可写入。
- ArkWeb 原生 HTML5 `drag/drop` 在 RV2 RISC-V 镜像上不稳定，曾出现拖动即闪退。因此 OpenHarmony 运行时不再使用 `draggable`、`dataTransfer`、原生 `drag/drop`、`setPointerCapture`。
- 当前新增 OpenHarmony 专用自定义拖拽层：
  - 触屏使用 `touchstart/touchmove/touchend`。
  - 鼠标使用 `mousedown/mousemove/mouseup`。
  - 拖动过程中只移动轻量 `.oh-drag-ghost` 预览层。
  - 松手时通过坐标和 `elementFromPoint`/近邻槽位检测写入指令或操作数。
- 用户实测发现触屏可拖动指令积木，但小积木吸附仍需继续调试命中区域和滚动体验；鼠标路径已接入自定义拖拽，待下一轮真机确认。

当前建议验收顺序：

1. 鼠标拖 `addi` 到拼接区。
2. 鼠标拖 `x1` 到 `rd/rs1/rs2` 槽位。
3. 触屏拖 `x1` 到槽位。
4. 如拖拽命中不准，用点击式编辑确认核心功能仍可完成。
5. 观察顶部工具栏是否横向紧凑，机器状态栏是否位于右侧。

当前仍需继续的问题：

- 自定义拖拽的小积木吸附命中半径、目标识别和触屏滚动手感仍需板端实测调参。
- 7 寸屏上若用户缩放页面，布局应保持左到右工作流，不应回退到上下堆叠。
- 保存/导入仍主要依赖 Web 能力，后续建议接入 ArkTS 原生文件桥接。
