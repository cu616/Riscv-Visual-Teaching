# 工程目录与代码分区说明

本文档面向后续参与开发的大创成员，用来快速理解当前仓库的分区、每个关键文件的作用，以及修改功能时应该从哪一层入手。

## 当前主线

当前项目存在两套实现：

- `app/`：当前主线工程。它是非 Blockly 自研积木 Web MVP，后续优先改造成桌面版，并继续打磨真实长方体上下贴边拼接。
- `self-desktop/`：当前主线的非 Blockly Electron 桌面壳，直接承载 `app/` 页面，用于形成可双击运行的 Windows 桌面演示程序。
- `openharmony-port/`：OpenHarmony / 香橙派移植原型。它把 `app/` 静态资源复制到 rawfile，并用 ArkTS + ArkWeb 承载本地页面，作为后续 HDC 真机部署入口。
- `desktop/`：Blockly + Electron 迁移验证版。它保留为技术验证，用来参考 TypeScript 化、保存加载、Electron 打包和 Blockly 工作区能力，但不再作为最终产品外观主线。

团队协作时，主线功能优先修改 `app/`、`self-desktop/`、`openharmony-port/` 和 `docs/`；Blockly 验证经验可以参考，但不要把 Blockly 默认拼图外观当成最终要求。`desktop/dist/`、`desktop/release/`、`desktop/node_modules/`、`desktop/.cache/`、`self-desktop/release/`、`openharmony-port/entry/build/`、`openharmony-port/build/`、`openharmony-port/.hvigor/`、`openharmony-port/oh_modules/` 是生成物或依赖目录，不应手动提交。

如果文档之间出现冲突，先看 `docs/文档状态与路线索引.md`。早期文档中关于“Blockly 正式主线”“固定右侧数据流面板”“PC 大卡片”的描述，已经被后续路线更新覆盖。

### Blockly 桌面版提交规则

`desktop/` 目录本身可以提交到仓库。应提交源码、配置、锁文件和维护脚本，包括：

```text

desktop/index.html
desktop/vite.config.ts
desktop/tsconfig*.json
desktop/electron/
desktop/src/
desktop/scripts/
```

不要提交生成物、依赖和缓存：

```text
desktop/node_modules/
desktop/dist/
desktop/dist-electron/
desktop/release/
desktop/.cache/
desktop/downloads/
desktop/manual-win-*/
desktop/manual-win-log-*/

```

`.gitignore` 已按这个边界配置。提交 Blockly 桌面版时不要使用 `git add -A` 盲加全仓库，当前仓库还包含 OH 资料手册和 `ohos_electron_hap/` 参考工程，若只提交 Blockly 桌面版，应使用定向 `git add desktop .gitignore docs/工程目录与代码分区说明.md`。

## Electron 层

| 文件 | 作用 |
| --- | --- |
| `desktop/electron/main.ts` | 创建桌面窗口。开发模式加载 Vite dev server，打包模式加载 `dist/index.html`；同时记录运行日志用于定位白屏、资源加载失败等问题。 |
| `desktop/electron/preload.ts` | Electron preload 入口。目前保持最小化，后续如果需要文件系统能力，应通过这里暴露安全 API，而不是在渲染层打开 Node 权限。 |

当前白屏排查结论：Blockly 不需要账号、注册或 API。白屏来自打包后的前端模块加载问题，例如 `file://` 下无法解析 `blockly/core` 这种裸模块名，或者依赖包下载不完整导致构建产物异常。

## 前端入口与总状态

| 文件 | 作用 |
| --- | --- |
| `desktop/src/main.tsx` | React 挂载入口，把 `App` 渲染到页面。 |
| `desktop/src/App.tsx` | 桌面端总控制器。集中管理当前案例、Blockly workspace、解析结果、机器状态、显示进制、单步执行和运行到结束。 |
| `desktop/src/styles/app.css` | 全局布局、面板、Blockly 工作区、机器状态、数据流区域等样式。 |

`App.tsx` 的核心思路是：

1. 从 `TEACHING_CASES` 加载默认案例。
2. 把案例传给 `WorkspacePane`，由 Blockly 生成 `RawInstruction[]`。
3. 用 `parseProgram` 把原始指令解析为可执行 `Instruction[]`，同时解析标签。
4. 用户点击单步或运行到结束时，调用 `executeInstruction` 更新 `MachineState`。
5. 右侧机器状态和数据流面板根据最新状态刷新。
6. 保存案例时，把 `instructions`、`initialState`、`displayBase` 和 `workspace` 一起写入 `.riscvteach.json`。

## 指令与模拟核心层

| 文件 | 作用 |
| --- | --- |
| `desktop/src/core/types.ts` | 全项目共享类型，包括 `RawInstruction`、`Instruction`、`MachineState`、`TeachingCase` 等。 |
| `desktop/src/core/instructionDefs.ts` | 指令定义中心。每条指令的 opcode、类型、颜色分类、字段顺序、中文说明和 help 都在这里。新增指令通常先改这里。 |
| `desktop/src/core/parser.ts` | 把 `RawInstruction[]` 解析为可执行指令，处理汇编格式化、标签映射、错误检查。 |
| `desktop/src/core/simulator.ts` | RISC-V 教学模拟器。根据当前 PC 执行一条指令，更新寄存器、内存、PC、日志和动画计划。 |
| `desktop/src/core/examples.ts` | 内置教学案例。新增指令后应增加对应案例，方便演示和验收。 |
| `desktop/src/tests/core.test.ts` | 核心逻辑测试。验证解析、模拟执行、特殊规则，例如 `x0` 恒为 0。 |

新增一条指令的推荐流程：

1. 在 `instructionDefs.ts` 增加指令字段顺序和类别。
2. 在 `parser.ts` 确认汇编格式是否正确，例如 `lw rd, imm(rs1)` 的立即数必须位于 `rd` 和 `rs1` 之间。
3. 在 `simulator.ts` 增加执行语义。
4. 在 `examples.ts` 增加教学案例。
5. 在 `core.test.ts` 增加测试。
6. 运行 `npm.cmd --prefix .\desktop run check` 和 `npm.cmd --prefix .\desktop run test:core`。

## Blockly 与指令转换层

| 文件 | 作用 |
| --- | --- |
| `desktop/src/parser/blocklyToInstruction.ts` | 把 Blockly 工作区转换为 `RawInstruction[]`。它会读取指令块连接的小积木，并按工作区顺序输出指令。 |
| `desktop/src/parser/instructionToBlockly.ts` | 把内置案例或保存文件中的指令重建为 Blockly workspace JSON，用于加载示例。 |

这个分区是 Blockly 与核心模拟器之间的桥。核心层不应该直接依赖 Blockly；Blockly 层也不应该直接执行指令。

| `desktop/src/components/AssemblyPreview.tsx` | 汇编预览区，展示 Blockly 解析后的指令文本或解析错误。 |

| `desktop/src/components/DatapathView.tsx` | 数据流可视化区。目前是抽象流水路径演示，后续可替换为更像 CPU 数据通路的组件。 |
| `desktop/src/components/ExampleGallery.tsx` | 内置案例列表，点击后加载到 Blockly 工作区和机器状态。 |
| `desktop/src/components/WorkspacePane.tsx` | Blockly 工作区 UI，见“Blockly 积木层”。 |

UI 层只负责展示和交互，不应在组件里重复实现指令语义。遇到“指令算错了”，应优先检查 `core/simulator.ts`；遇到“汇编顺序错了”，应优先检查 `core/parser.ts` 和 `parser/blocklyToInstruction.ts`。

## 案例保存格式

| 文件 | 作用 |
| --- | --- |
| `desktop/src/cases/caseFormat.ts` | `.riscvteach.json` 的序列化和解析。 |

保存文件应尽量与内置案例结构一致，至少包含：

- `version`
- `id`
- `title`
- `instructions`
- `workspace`
- `initialState`
- `displayBase`

这样用户保存的文件和软件自带样例可以走同一套加载流程。

## 当前构建与白屏相关注意事项

- `desktop/vite.config.ts` 必须保留 `base: "./"`，否则打包后 `file://` 会把资源路径解析到磁盘根目录，导致白屏。
- Blockly 是本地 npm 库，不需要账号、注册、API key 或联网调用。
- 如果控制台出现 `Failed to resolve module specifier "blockly/core"`，说明最终产物里仍有浏览器不能解析的裸模块导入，需要重新检查 Blockly 依赖完整性和 Vite 打包结果。
- 当前工作区曾从 npm 缓存恢复过 `blockly_compressed.js`、`blocks_compressed.js`，因为本机 `desktop/node_modules/blockly` 一度下载不完整。
- `desktop/dist/` 中的临时 shim 只用于排查当前已打包 exe 的模块解析问题；长期方案仍应以完整依赖 + 正常 Vite 构建为准。

## 团队协作约定

- Git/GitHub 提交、分支、PR、合并冲突和旧分支清理流程统一参考 `docs/Git协作流程与分支规则.md`。
- `main` 只保留当前可运行、可展示版本；新功能从最新 `main` 新建功能分支，经过 Pull Request 合入。
- 提交前必须运行 `git status --short`，只 `git add` 本次任务相关文件，不要盲目 `git add -A`。
- 新增正式功能优先走 `desktop/src/core`、`desktop/src/parser`、`desktop/src/blocks`、`desktop/src/components` 四层分工。
- 新增指令时不要只改 Blockly 外观，必须同步补齐定义、解析、模拟、案例、测试。
- 修改 UI 时不要把教学规则写死在组件里，教学规则应放在 `core/`。
- 修改保存格式时必须同时考虑内置案例和用户保存文件。
- 构建产物、依赖目录、临时排错目录不提交。
- 重要需求和阶段性决策写入 `docs/`，避免只留在聊天记录里。
