# 机器状态格动画重构方案

更新时间：2026-05-09

## 1. 背景

旧的数据流可视化采用抽象节点和连线表达 PC、寄存器、ALU、内存、回写等阶段。这个方式能说明“有数据流”，但学生不容易把动画和右侧真实变化的寄存器、内存方格对应起来。

下一阶段动画应改为围绕“机器状态格”展开：寄存器格、内存格、PC、当前指令积木和执行日志共同构成解释对象。动画重点不再是抽象时序图，而是让学生看到“哪些格子被读取、哪些格子参与运算、哪个格子被写回、PC 如何变化”。

## 2. 设计原则

1. 动画锚点必须来自真实机器状态：寄存器格、内存格、PC 和当前指令积木。
2. 动画只解释教学抽象，不冒充完整 CPU 微架构。
3. 数值变化优先于装饰效果：读取高亮、运算汇聚、写回闪烁、PC 变化。
4. 动画层不阻挡操作，应使用 `pointer-events: none`。

## 3. 推荐界面结构

建议在机器状态页签里增加一个轻量覆盖层：

```text
assist-panel
└─ machine tab
   ├─ state-animation-dock
   ├─ workspace-harmony-panel
   ├─ register-grid
   ├─ memory-grid
   └─ state-editor
```

`state-animation-dock` 是当前动画表达式的固定挂载点，位于机器状态页签顶部、机器状态标题上方。它只负责展示当前指令内部的表达式，例如 `x1=12 & x2=10 => x3=8`，不保存业务状态。

`workspace-harmony-panel` 是 OpenHarmony 展示栏。若它处于打开状态，执行动画时 `state-animation-dock` 会临时取代该展示栏；动画结束后恢复 OpenHarmony 展示。这样课堂演示时学生先看到当前机器计算，再回到硬件展示信息。

PC 不再作为机器状态栏内的大卡片展示，避免占用寄存器/内存区域空间。PC 已迁移到顶部执行进度条旁，以 `PC <value>` 的紧凑形式显示；执行到 PC 阶段时只做小高亮。

## 4. 动画阶段模型

每条指令执行后生成统一脚本：

```js
[
  { phase: "read", targets: ["x1", "x2"] },
  { phase: "compute", op: "+", inputs: ["x1", "x2"], output: 12 },
  { phase: "write", target: "x3", oldValue: 0, newValue: 12 },
  { phase: "pc", oldValue: 2, newValue: 3 }
]
```

不同指令只需要生成不同脚本，不要每类指令单独写一套 DOM 操作。

当前实现文件：

- `app/src/state-animation.js`：生成并播放机器状态格动画。
- `app/src/app.js`：在单步/自动执行后调用 `playStateAnimation(result, context)`，并在动画期间切到右侧“机器”辅助栏。
- `app/styles.css`：定义 `state-animation-dock`、`state-expression-badge`、寄存器/内存高亮、飞行数值卡片和 PC 小高亮。

OpenHarmony 移植版通过 `npm run oh:check` 同步到：

```text
openharmony-port/entry/src/main/resources/rawfile/app/
```

## 5. 指令类型动画预案

### R 型算术逻辑

示例：`add x3, x1, x2`

1. `x1` 和 `x2` 寄存器格发蓝光，表示读取两个源操作数。
2. 两个值以小标签形式从 `x1`、`x2` 飞向中间运算徽标 `+`。
3. 运算徽标短暂显示 `value1 + value2 = result`。
4. `x3` 发绿光，显示 `旧值 -> 新值`。
5. PC 格发光，显示 `PC + 1`。

逻辑类使用 `&`、`|`、`^`、`<<`、`>>` 等徽标。

2026-05-09 细化要求：

- 不再只用两个蓝色小卡片靠近来暗示“发生运算”。
- 源操作数必须显示为带寄存器名和值的表达式片段，例如 `x1=12`、`x2=10`。
- 运算符必须作为独立视觉中心出现，例如 `&`、`|`、`^`、`<<`、`>>u`、`>>s`。
- 结果必须显示目标寄存器和值，例如 `x3=8`。
- 表达式整体形态应接近：

```text
x1=12 & x2=10 => x3=8
x1=-16 >>s x2=2 => x5=-4
```

这些内容是按当前执行状态动态生成的，不是写死的示例文案。

### I 型算术逻辑

示例：`addi x2, x1, 8`

1. `x1` 寄存器格发蓝光。
2. 立即数从当前指令积木对应槽位浮出。
3. `x1` 的值和立即数飞向运算徽标。
4. 结果写回 `x2`。
5. PC 更新。

重点：立即数不是寄存器，不应在寄存器区伪造来源。

### 访存读取：`lw`

1. 基址寄存器发蓝光，偏移量从指令积木槽位浮出。
2. 地址计算徽标显示 `base + offset = address`。
3. 对应内存地址格发蓝光，表示读取内存。
4. 内存值飞向目标寄存器。
5. 目标寄存器发绿光写入新值。
6. PC 更新。

当前地址计算表达式应显示为：

```text
x1=16 + imm=0 => addr=16
```

其中 `x1=16` 来自基址寄存器，`imm=0` 来自指令立即数字段，`addr=16` 是计算出的内存地址。

### 访存写入：`sw`

1. 基址寄存器和偏移量计算目标地址。
2. 源寄存器发蓝光，表示读取要写入的数据。
3. 数据从源寄存器飞向目标内存地址格。
4. 内存格发绿光，显示旧值到新值变化。
5. PC 更新。

重点：`lw` 是“内存到寄存器”，`sw` 是“寄存器到内存”，动画方向必须相反。

### 分支

1. 源寄存器格发蓝光。
2. 比较徽标显示条件，例如 `x1 == x2 ?`。
3. 条件成立时目标标签积木和 PC 同时高亮，PC 跳到目标行。
4. 条件不成立时 PC 显示 `PC + 1`。
5. 执行日志同步解释“为什么跳转/为什么不跳转”。

### 跳转

1. PC 格发蓝光，显示当前 PC。
2. 若写回返回地址，目标寄存器格发绿光。
3. 目标标签或目标地址高亮。
4. PC 格显示跳转后的值。

## 6. 技术实现建议

建议新增模块：

```text
app/src/state-animation.js
```

职责：

- 根据执行结果生成动画脚本。
- 根据寄存器名、内存地址、PC、指令 id 查找 DOM 锚点。
- 管理动画层中的飞行标签、连线、阶段徽标。
- 提供 `playStateAnimation(result, context)` 和 `clearStateAnimation()`。

`app/src/app.js` 只负责在单步执行后调用动画模块，不直接写复杂动画细节。

## 7. 验收标准

- 执行 `add x3, x1, x2` 时，学生能看出 `x1/x2` 被读取，`x3` 被写入。
- 执行 `lw` 和 `sw` 时，学生能看出数据方向相反。
- 执行分支时，学生能看出比较结果和 PC 去向。
- 单步执行时自动播放完整动画，不需要学生额外点击“显示动画”。
- 自动执行时也播放完整动画，不降级为快速高亮。
- 每条指令的动画时长必须和步骤进度条同步：进度条应表达当前指令动画播放进度，而不是只在指令执行完成后跳变。
- 动画结束后机器状态格仍保持最终值，不出现临时残影。
- 动画不阻挡拖拽、缩放、辅助栏切换。
- PC 不再占据机器状态栏大块空间；顶部进度条旁能看到当前 PC。
- 执行动画时，右侧辅助栏自动切到“机器”页，表达式卡片出现在机器状态标题上方。
- 若 OpenHarmony 展示栏已打开，动画期间表达式卡片临时取代它；动画结束后 OpenHarmony 展示栏恢复。
- AND/OR/XOR/移位/访存地址计算等指令不能共用一个含糊的“两个卡片靠近”效果，必须显示具体符号或关系。

## 8. 暂不实现内容

- 不做真实五级流水线。
- 不做缓存、总线竞争、中断等系统级细节。
- 不做复杂 3D 或大面积粒子效果。
- 不把动画结果作为模拟器状态来源，模拟器仍是唯一状态真相。

## 9. 待确认问题

已确认：

1. 单步执行时自动播放完整动画，不额外设置“显示动画”开关。
2. 自动执行时播放完整动画，不只做快速高亮。
3. 每一步运行时间和步骤进度条必须同步，后续实现时需要把“动画播放中”的阶段纳入执行控制状态。
4. “补缺练习”不是当前需求，是语音转文字误差，后续不纳入本轮动画重构范围。
5. 每条指令默认动画时长先采用 `900ms - 1400ms` 区间，第一版以 `1x = 1200ms` 为基准。
6. 自动执行允许调节速度，第一版提供 `0.5x / 1x / 1.5x`。
7. 进度条同时显示“第几条 / 总条数”和当前条动画进度，但文案保持短，例如 `2/5 · 64%`。

仍待细化：

1. 不同类别指令是否需要不同默认时长，例如访存和分支略慢、普通 ALU 略快。
2. 速度调节是否只影响自动执行，还是单步动画也同步受影响。当前实现建议两者都受影响，保持一致。
