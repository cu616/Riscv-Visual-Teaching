# 技术路线决策与阶段复盘

更新时间：2026-05-09

## 1. 当前最终决策

经过自研积木原型、Blockly 迁移验证、Electron 打包排错和 OpenHarmony 可行性讨论后，当前项目路线确定为：

```text
主线：非 Blockly 自研积木桌面版
保留：Blockly 迁移版作为技术验证
远期：OpenHarmony 采用 ArkWeb/WebView 先承载，再逐步原生化
```

这意味着后续正式产品不再强行迁移到 Blockly 默认积木外观，而是回到最初更符合本项目表达目标的“真实长方体积木上下贴边拼接”设计。

2026-05-09 补充：旧的独立抽象数据流面板已经暂停，当前动画说明方向改为“机器状态格动画”。PC 不再占据机器状态栏大卡片，而是显示在顶部执行进度条旁；动画表达式挂载到右侧机器页顶部，并可临时取代 OpenHarmony 展示栏。文档冲突时先看 `docs/文档状态与路线索引.md`。

## 2. 为什么主线回到自研积木

本项目的核心不是做通用图形化编程工具，而是为 RISC-V 教学做一个能解释“指令由操作码、寄存器、立即数、标签等字段拼接而成”的演示软件。

用户反复确认的最终视觉目标是：

- 指令积木是上层长条，例如 `add`、`addi`、`lw`。
- 操作数、立即数、地址、标签等小积木位于指令积木下方。
- 大积木和小积木通过上下相邻的长方形边贴合，而不是把小积木嵌入大积木内部。
- 标签应作为左侧贴边的小积木或标签帽，与指令主体形成积木感。
- 程序顺序按画布中指令块的纵向位置从上到下判断，同时允许拖拽排序、复制、移动和保存。

Blockly 的默认范式更偏向“拼图形卡口”和“右侧/内嵌式输入”。即使可以通过自定义 renderer 改成方形卡口，仍然很难自然表达本项目需要的上下两排、长方体贴边、操作数独立拼接的真实积木感。继续强行改造 Blockly 会消耗大量工作量，而且最终外观仍可能不符合比赛草案中的产品构想。

因此，后续主线应回到 `app/` 的自研积木交互，并把它封装成桌面软件。

## 3. Blockly 迁移版的价值

虽然 Blockly 不再作为最终主线，但这段迁移不是无效工作。它验证和沉淀了以下内容：

- Electron + React + TypeScript + Vite 的桌面工程结构。
- RISC-V 指令定义、解析、模拟器、教学案例、机器状态显示的模块化拆分方式。
- 拖拽连接、连接约束、工作区序列化、保存加载等成熟图形化编程能力的参考实现。
- Windows 打包过程中 `file://` 资源路径、裸模块导入、Electron 二进制、app-builder 下载失败等问题的排查经验。
- Blockly 不需要账号、注册或 API，白屏问题主要来自前端构建和 Electron 打包资源加载。

后续可以把 `desktop/` 当作技术验证仓库：

- 参考其中的 TypeScript 类型、指令定义和案例结构。
- 参考 Electron 桌面封装方式。
- 参考保存文件格式和工程文件思路。
- 不再以 Blockly 默认外观作为最终 UI 约束。

## 4. 阶段进度回顾

### 2026-04-29：自研 Web MVP

提交 `Add MVP app and reorganize docs` 建立了 `app/` 早期原型。

这一阶段完成了：

- 自研指令积木编辑区。
- 指令积木拖拽到画布。
- 操作数小积木、标签、立即数等素材。
- RISC-V 指令解析和模拟执行。
- 寄存器、内存、PC 状态展示。
- 数据流动画和教学解释。
- 示例案例与一键启动脚本。

这个版本最接近用户对“真实积木拼接”的产品设想，但工程仍偏单文件和 Web 原型，需要进一步桌面化、模块化和交互打磨。

### 2026-05-01 凌晨：指令集扩展

提交 `Expand RISC-V teaching instruction set` 扩展了常用教学指令。

主要新增：

- 算术、逻辑、移位、访存、分支、跳转等教学常用指令。
- `x0` 恒零提示。
- 存储单元十进制、二进制、十六进制显示。
- 初始化寄存器和内存的能力。
- 更多示例案例与核心测试。

这一阶段明确了后续开发必须严格校验指令格式和操作数顺序，例如 `lw rd, imm(rs1)` 中立即数应处于基址寄存器和地址表达之间，而不能简单放在最右端。

### 2026-05-01 夜间：Blockly 桌面验证版

提交 `Add Blockly desktop migration prototype` 新增了 `desktop/`。

这一阶段完成了：

- Electron + React + TypeScript + Vite + Blockly 工程。
- Blockly 自定义 RISC-V 指令块和操作数块。
- 案例加载、解析、模拟、机器状态、数据流区域。
- 保存与加载工程文件的方向验证。
- Windows 打包和白屏排查。

同时也暴露出关键问题：

- Blockly 默认积木范式和项目目标外观差距较大。
- 方形卡口可调，但上下贴边式长方体拼接很难自然实现。
- 打包链路对 Electron、app-builder 等二进制依赖较敏感。
- 手动修补 `dist/` 或 `release/` 只能临时排错，不能作为长期开发方式。

### 2026-05-03：路线收束

在比较两条路线后，当前决策为：

- 正式产品路线回到自研积木。
- 桌面端先采用 Electron 承载自研 Web UI。
- Blockly 继续保留为技术验证和工程参考。
- OpenHarmony 远期先用 ArkWeb/WebView 承载，再逐步评估 ArkUI 原生化。

## 5. 下一阶段开发重点

### 5.1 自研积木桌面版

优先目标是把 `app/` 的非 Blockly 原型改造成可运行的桌面版：

1. 抽离 `app/src/app.js` 中的积木编辑、解析、模拟、状态展示和机器状态格动画逻辑。
2. 建立更清晰的模块分区，避免主文件继续膨胀。
3. 用 Electron 封装自研 Web UI，形成可双击运行的 Windows 桌面程序。
4. 将保存、加载、示例案例、初始化机器状态、进制显示等能力纳入主线。
5. 针对真实积木拼接重做拖拽吸附：指令上排、小积木下排、标签左侧贴边。

### 5.1.1 2026-05-04 工程推进顺序

当前已经新增 `self-desktop/` 作为非 Blockly Electron 桌面壳，但本机 Electron 直接启动仍存在窗口不能稳定保持的问题。因此下一阶段工程采取“两层启动保障”：

1. 演示可用优先：`打开非Blockly自研积木桌面版.bat` 先稳定打开 `app/` 主线应用。它通过 `scripts/launch_non_blockly_app.ps1` 检查本地服务，必要时启动 `npm.cmd start`，再优先使用 Edge/Chrome 的 `--app=http://localhost:4173` 应用窗口模式打开，而不是普通浏览器标签页。
2. 桌面壳继续修复：保留 `self-desktop/`，继续定位 Electron 直接启动和 `electron-builder` 打包问题，目标仍是生成可双击 exe。
3. 主线开发不等待 Electron：真实积木吸附、保存加载、机器状态格动画增强等产品核心能力继续在 `app/` 中推进。

下一阶段的实际工程优先级调整为：

1. 稳定一键启动链路，保证答辩和组内演示随时可打开。
2. 拆分 `app/src/app.js`，优先抽离拖拽、吸附、渲染和执行控制。
3. 建立自研积木的真实吸附关系数据模型。
4. 实现自由小积木、自动吸附、拖出后字段为空和汇编预览报错。
5. 为 `app/` 主线增加 `.riscvteach.json` 保存与加载。
6. 修复 `self-desktop/` Electron 直接窗口启动，并完成 Windows 目录包打包。

### 5.2 保留 Blockly 验证版

`desktop/` 后续不再承担最终外观压力，但应保留：

- 作为 TypeScript 化工程样板。
- 作为 Electron 打包和桌面窗口验证样板。
- 作为保存/加载和案例结构参考。
- 作为对比 Blockly 与自研交互差异的技术说明材料。

### 5.3 OpenHarmony 路线

远期 OpenHarmony 推荐分两步：

1. 先用 ArkWeb/WebView 承载自研 Web UI。
2. 当比赛展示或性能体验需要时，再逐步把核心界面迁到 ArkUI。

这样可以最大化复用当前 Web 原型和后续 Electron 主线，降低一次性重写成本。

## 6. 维护提醒

- 不要把 `desktop/dist/`、`desktop/release/`、`desktop/node_modules/` 等生成物提交到 Git。
- 不要长期依赖手动修改打包产物来修复白屏，必须回到源码和构建配置解决。
- 文档统一使用 UTF-8，避免 PowerShell 默认编码导致中文乱码。
- 每次路线调整、需求取舍、关键问题排查都应写入 `docs/`。
- 后续 AI 接手时应先阅读本文件，再决定继续开发哪条工程线。
